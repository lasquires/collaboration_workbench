# Collaborative Research Workspace Implementation Plan

> For agentic implementers: use `superpowers:executing-plans` for inline implementation or `superpowers:subagent-driven-development` for coordinator-authorized bounded delegation. These are static implementation instructions; claims, dependencies, acceptance results and delivery status belong only in the SQLite workspace. Numbered steps deliberately replace live Markdown checkboxes.

**Goal:** Extend the local research dashboard into one durable, explainable workspace for tasks, source observations, questions, discoveries and collaboration.

**Architecture:** Keep the existing Python HTTP service, SQLite transaction boundary and plain JavaScript/SVG interface. Add normalized research records and bounded read projections behind `/v1`; retain existing `/api` adapters and global revision semantics. Deliver a durable occurrence-to-question-to-inbox loop before the wider collaboration interface.

**Tech stack:** Python standard library (`sqlite3`, `http.server`, `unittest`), SQLite foreign keys/FTS5, plain HTML/CSS/JavaScript/SVG, existing Node assertion fixtures. No graph database, frontend framework, hosted deployment or semantic model is required.

**Spec:** [Collaborative research workspace](../specs/2026-11-12-collaborative-research-workspace-design.md). Read it with this plan. It supersedes task-only product scope; it does not claim full native game parity.

## Global constraints

- One authoritative service/database per checkout. Migrations, imports and all ordinary writes go through the service; never mutate the live SQLite file from an import script or client.
- Preserve original task records, source archive, unknown fields, event history, aliases and unknown historical dates. No dual authority between JSON/files and SQL.
- Every project-owned identity and lookup is project scoped. Local actor labels are visibly unauthenticated; stable principals own agent sessions and votes.
- A task status, vote, hint or index publication cannot establish native truth. Findings and accepted evidence have explicit, independently enforced gates.
- Containment is a forest; dependencies form a separate DAG. Archives, redirects and reversible edits retain referenced history.
- No silent rebase on HTTP 409. Request-ID retries are idempotent; changed request content with the same ID conflicts.
- Matcher execution is at least once with idempotent effects. Publication remains available while matching is delayed or broken.
- Puzzilla-inspired map is the primary workspace; list and board are alternatives. Focus changes navigation only.
- Every eventual implementation slice requires a database task, exclusive write reservation, relevant checks and coordinator integration. This plan does not create or claim those records.

## Shared identity, schema and API contract

### Identity and migration mechanics

Use UUID text IDs for new internal identities. Retain existing `tasks.id` as the legacy storage key to avoid rewriting event foreign keys. Add a unique immutable `uid` and `project_id` to each task; v1 returns the UUID as `id`, plus `alias` and `legacy_id`. Compatibility endpoints retain the exact old task ID shapes. All new task references use `tasks.uid`, and resolution accepts UUID or a unique project alias. New tasks receive a UUID and a user-chosen or generated non-reused legacy key. `record_json.id` remains the legacy key for compatibility; v1 editable fields exclude it. Renames add aliases and change display text, never identity. Do not claim the old schema already used opaque IDs.

Introduce sequential schema versions rather than one all-or-nothing future schema. Migrations run under the service's exclusive startup lock and `BEGIN IMMEDIATE`, with explicit rollback and supported-version checks. The stopped-writer migration preflight uses SQLite backup API to a new path, verifies integrity/foreign keys and records source/checkpoint hashes. Preserve `store_id`; increment global revision once for each committed migration/import transaction. No database downgrade in place: restore a verified backup under the old compatible service. Unknown newer schemas refuse startup.

All editable entities have integer `revision >= 1`, `created_by`, `created_at`, `updated_at`, nullable `archived_at`; append-only versions/observations/events have attribution and recorded time instead. `source_created_at`, `discovered_at` and `ingested_at` are separate nullable fields; never fill historical nulls from migration time. For project-owned tables use `UNIQUE(project_id,id)` and composite foreign keys `(project_id,target_id)` to enforce isolation, in addition to API checks. Global principals/store metadata are explicit exceptions.

### Versioned HTTP envelope

All v1 reads return `{api_version:"research-workspace/v1",project_id,revision,items,next_cursor,coverage}` for lists; details replace `items` with a named record. `revision` remains the existing global string. Records include their integer `record_revision`. Coverage names source and indexed/uncovered scope, not just a boolean. Cursor is opaque, tied to project/filter/snapshot and an ordered `(created_at,id)` or event sequence; changing filter invalidates it. Expired snapshot cursor returns 409 with `restart_required`, never silently skips rows.

Mutations use `{project_id,actor:{principal_id,session_id},request_id,expected_revision,operations}` at `POST /v1/transactions`. Initially `expected_revision` is mandatory global CAS. Once record CAS is delivered, add explicit `concurrency_mode:"records"` and `expected_records:[{type,id,revision}]`; omit global CAS only in that explicit mode. Structure writes also name all affected parents/ancestry aggregate `structure_revision` values. The server derives the affected set and rejects missing guards. Legacy `/api` always retains global CAS. Do not reinterpret integers as global strings or silently opt clients into record mode.

Successful mutations return `{revision,event_cursor,changed_records,request_id}`. Errors are `{error,code,conflicts:[{type,id,expected,actual}],latest_revision}` with 400 validation, 403 capability, 404 scoped absence, 409 conflict, 413 size, 503 transient store failure. A foreign-project ID returns 404 before including names in errors. Preview endpoints are reads and do not allocate claims or mutate records.

The first release uses service-configured page, batch, worker and lease limits, returned by `/v1/projects/{id}/capabilities`. Start measurement fixtures at 100 list items, 250 neighborhood nodes, 500 records/batch and the existing 8 MiB body ceiling. Reject over-limit input with limits in the response; tune these proposed defaults from the fixture report before enabling live ingestion. Lease duration is configured and explicit in claim response; tests inject a clock rather than sleeping.

## Delivery slices

Commands below use `python`; use the workspace-configured interpreter if necessary. No test may open `analysis/roadmap.sqlite3`.

### Slice 4 — Deterministic matching, replay and durable inbox (first full research loop)

**Depends on:** Slice 3; map can proceed independently. **Files:** `tools/roadmap_matcher.py`, research/store/schema/server/CLI modules, new `tests/test_research_matcher.py`, `tests/test_research_recovery.py`.

Pure function `match_question(question_revision:dict,candidate:dict,rule:dict)->dict|None` returns compared fields, constraints, support hashes and human explanation. Candidate type is `observation` (immutable observation ID), or `finding_revision`; an occurrence is a grouping identity, never a mutable extracted-value candidate. `evidence_revision` belongs to that candidate, not an unrelated latest occurrence value.
2. Start `exact-scoped/v1`: exact identifier plus explicit artifact/build, namespace/class, plist path, native mapping ID or type/offset constraints; approved aliases may relate scoped occurrences. OR groups must be explicit criteria arrays; all fields within a group are AND. No cross-project matching. Bare broad identifiers require `allow_low_specificity:true` and produce clearly labeled low-specificity hints. Never normalize case outside a registered namespace rule.
3. Upsert key is `(project_id,question_id,criteria_revision,candidate_type,candidate_id,evidence_revision,rule_id,rule_version)`. Compute semantic fingerprint as SHA-256 of canonical `{project_id,question_id,criteria_semantics,candidate_type,candidate_id,matched_fields,scope_constraints,support_hashes}`; exclude rule version/editorial text. Save actual matched values and hashes. Same fingerprint on rule upgrade carries prior decision with an explicit decision-provenance link; new fingerprint creates a successor without overwriting a dismissal. Editorial updates increment presentation only; criteria/source-support changes increment their respective revisions. Distinct question/candidate IDs prevent revision-1 collisions.
4. `consume_outbox(store,project_id,limit:int,now:str)->dict` processes publication and new/edited-question events both directions in stable ID order. Persist fanout page cursor for large events. Job transaction commits hint/inbox effects and cursor/ack together; retries are safe even if ack is repeated. `replay_rule(store,project_id,rule_id,rule_version,limit:int)->dict` persists replay progress. A bounded service worker wakes on commits and periodic retries; CLI `process-jobs --limit` is the deterministic recovery path. No model watcher and no new server process per event.
5. Subscription recipients include eligible explicit subscribers and affected task owners, deduplicated by principal. Digest by project/question/source run and meaningful transition; inbox key `(recipient,semantic_identity,transition_key)` deduplicates retries. Do not notify again for carried editorial/rule decisions. Check project membership at match and delivery time. Hint review states and per-recipient read state remain separate. Useful does not resolve a question; resolution requires answer/evidence gate. Retraction stales dependent hints and sends evidence-review notices to accepted conclusions without rewriting them.
6. Expose `/v1/hints`, `/v1/subscriptions`, `/v1/inbox`, `/v1/replay-jobs`, `/v1/processing-status`; failure shows lag/errors while published observations remain readable. Reproduce an explanation from pinned candidate/question/rule values after restart.

**Gate:** `python -m unittest tests.test_research_matcher tests.test_research_recovery`. ## Review focus and failure ownership

| Input/condition | Expected behavior and owning fixture |
|---|---|
| Two extractors disagree at the same source location | Immutable observation IDs coexist; no publication-order winner; Slices 3–4 ingestion/matcher tests |
| Required child archived/moved after parent acceptance | Reopen required ancestors atomically or reject; Slice 5 structure/progress tests |
| Old client writes after new research edit | Existing global revision rejects stale write; Slice 1 foundation and Slice 5 record-mode compatibility tests |
| A registered file changes between preview and registration | Hash guard rejects stale snapshot; Slice 6 document and Slice 8 recovery tests |
| User edits while selected task merges or becomes inaccessible | Draft survives; redirect/history and explicit reconciliation appear; Slice 7 UI/browser fixtures |

## Sequencing, ownership and design resolutions

The first backend assignment is Slice 1 only, ending with the frozen neighborhood/context fixture and unchanged legacy tests. The first independent UI assignment is Slice 2 only, consuming that fixture; it can run alongside Slice 3 when paths are exclusive. The coordinator owns shared schema/store/server integration and reservations; workers must not concurrently edit these files. Subsequent backend slices are sequential wherever their file reservations overlap. Do not turn this document into a parallel status board.

No blocking architecture contradiction remains if the compatibility decisions above are adopted. Three tradeoffs require explicit visibility during review: legacy task storage keys remain while new public identities are UUIDs; imported historical done states may lack verified acceptance; unresolved source artifact identities are preserved as incomplete provenance rather than promoted to native evidence. The spec's occurrence revisions must mean immutable observation history plus explicit reconciliation, never a latest-observation winner. Hint candidates therefore pin observation IDs. Local stable principals prevent accidental vote multiplication but are not authentication; remote identity is a separate delivery gate.

The plan covers every design section: source identity/occurrence observations (3), structure/history (5), lifecycle/progress/context (1,5), deterministic indexing/replay (3,4), Puzzilla navigation (2,7), versioned API and compatibility (1,5), documents/help/discussion (6,7), recovery/security/migration boundaries (3,8). Numerical limits are proposed measurable local defaults, not source-derived requirements. Full semantic search, autonomous agent spawning, cross-project sharing and remote deployment remain outside the initial local release.
