# Live controls and compact review protocol

The owner opts into a host URL and a private credential-file path. Git-only remains usable. Existing live service owns the durable outbox and reviewed-command receipts; leases remain a separate explicit protocol. This layer keeps full portable reviews and choices in private typed JSON cache, exposing at most20 conflict rows and8192 characters of a full value per read. Browser recovery stores only bounded action bodies with IDs and choice modes, never bundles, raw field values or token contents.

Coordinator owns backend/integration. UI worker owns only docs/workspace-live.js and tests/workspace_live.cjs; no commits/staging/descendants. Browser global/CommonJS export WorkspaceLive with createSession and create. create({api,notice,getContext,onDirty}) renders into #liveWorkspace. getContext returns {projectId,activePanel,hostOwner}; active panel name live. Return {load,discard,state}; state exposes projectId and pendingBody for dashboard recovery routing. onDirty must not clear another project/panel draft. All authored content is textContent, never HTML. Show local-only claims separately from acknowledged host leases; acknowledgment never proves current expiry/ownership or full data sync.

## HTTP contract

All POSTs use JSON and current WorkspaceAccess options through injected api; shared-mode live controls require host owner. GET /v1/projects/{id}/capabilities adds capabilities.host_owner; trusted local mode is a host owner. GET /v1/live-status?project_id remains safe status. Existing POST /v1/live-configure takes {project_id,enabled,url?,token_file?}; blank optional fields mean reuse saved settings. Disabling preserves pending work; changing host while a UI command is pending is forbidden. POST /v1/live-sync takes {project_id}. No credential content enters the browser, only its local path supplied by the owner. No automatically submitted mutations or lease heartbeats.

New review routes:
- POST /v1/live-ui-preview {project_id,kind}, kind join|host|local. It gets the actual backend preview, binds owner/project/local store/endpoint/authenticated remote principal+store, and returns a page. Existing reviewing choices, prepared or pending command require explicit discard/confirmation before replacement.
- GET /v1/live-ui-state?project_id=...&offset=0 returns a page or {project_id,phase:"idle",items:[]}. Read-only; safe to call on reload. It does not submit anything.
- GET /v1/live-ui-value?project_id=...&review_id=...&key=...&side=local|remote|base&offset=0 returns {project_id,review_id,key,side,offset,text,next_offset,length,digest}. Read on demand, render literal text, expose further pages. Values in ordinary pages are previews and visibly marked truncated.
- POST /v1/live-ui-choices {project_id,review_id,offset,expected_draft_revision,request_id,choices}. choices contains exactly the current page keys, values ""|local|remote, no defaults. A request ID has exact-body replay semantics (latest32 private receipts); duplicate returns choice_ack_request_id and a current page. Changed body/revision rejects409. The browser persists this small exact action before POST and retries it after uncertain replies/reload.
- POST /v1/live-ui-prepare {project_id,review_id,expected_draft_revision,acknowledged:true}. Every conflict must have an explicit saved choice. Recheck current actual review and host identity; no implicit rebase. Freeze command_id (the backend command digest) and phase prepared. Repeating the exact preparation returns its current page, never submits. Persist the small preparation action before POST too.
- POST /v1/live-ui-submit {project_id,review_id,command_id}. Persist this exact handle action in sessionStorage before POST. Service marks pending before calling join/resolve, then accepts only a matching backend reviewed_command acknowledgment. Returns a page with phase acknowledged, pending or rejected. HTTP/network failure leaves pending recovery, no fresh body/ID. A verified not-applied stale revision can return phase rejected and allow a new explicit review; an ambiguous outcome cannot be discarded.
- POST /v1/live-ui-discard {project_id,review_id}. Explicitly discards reviewing/prepared/rejected/acknowledged UI state; refuses pending outcomes. Never discards the actual live outbox.

Page: {project_id,review_id,kind,phase,draft_revision,command_id,selected_count,total_conflicts,summary,offset,next_offset,items,result,error,host_url,remote_store}. summary is a mapping table -> mapping change status -> count, including compatible rows. items are [{key,table,field,entity_key,choice,local,remote,base}]. Each side is {present,preview,length,digest,truncated}; preview is canonical value text <=2048 chars. Choices save per page; next/previous navigate only after local unsaved selections saved or explicitly discarded. Saved server choices persist through reload. Acknowledgment checkbox is explicit; it is not preselected after a reload.

For kind host, choice local means keep HOST current value and remote means use THIS APP queued value. For join/local, local means keep THIS APP and remote means use HOST. State acknowledged confirms that command only; result.state/phase may still require local review or report offline/pending. Owner/project/host mismatch fails closed. Unsupported/corrupt private state never gets silently reset. API409 requires an explicit reread/review, never automatic rebase.

## Durable terminal confirmations

Private ui-outcomes.json retains the latest 256 terminal command receipts within a 2 MiB bound, scoped to local store, project and owner. An acknowledged receipt is persisted before the active review manifest. A crash between these writes can recover the known result without executing again. Discarding an active review preserves these bounded historical receipts. An explicit submit with a retained exact handle returns historical_only:true, current_access_checked:false and recorded_at without contacting a host. This confirms only the previously recorded command, never current access, current data synchronization or a current lease. Corrupt ledger data fails closed and is not silently reset. Receipt eviction does not authorize replay of an obsolete handle; it falls back to the active handle checks.

## Host claims

Existing POST /v1/live-claims-read {project_id,task_id,cursor?}, /live-claims-preview {project_id,operation}, /live-claims-submit {project_id,review_id}. Preview operation {op:claim_task|heartbeat_claim|release_claim|handoff_claim,task_id,rationale,lease_seconds?,reserved_paths?,to_principal_id?}; claim only accepts optional reserved_paths and lease_seconds, heartbeat lease_seconds, handoff lease_seconds/to_principal_id, release no extras. Preview returns {review_id,request,task,scope:"host"}. Submit accepts only stored ID and has its own durable recovery.

New POST /v1/live-claims-review {project_id} reads saved private review without network or mutation, returning {scope:"host",state,review,result,acknowledgment_is_current_lease:false}. Its metadata is historical; only claims-read revalidates current host leases. Persist claim-submit handle in a distinct session key before posting; reload only reads status/saved review. No auto acquire/renew/retry. Show expiry/released state and fresh-read availability separately, including read failure/unknown when offline. Do not claim shared ownership from local claims.

## Lease outcome recovery across previews

The host claim backend retains at most 256 small terminal outcome receipts under a 2 MiB bound. The private ledger is bound to the local store, project and actor and is stable across endpoint changes; each row retains its original endpoint, authenticated remote actor and installation. A terminal receipt is durable before active claim state publication. Confirming an exact retained handle returns historical_only/current_access_checked:false without host execution, including a typed not_applied receipt for a known rejection. The owner HTTP claims-submit route uses this confirmation wrapper while the lower-level submit API preserves its existing exception behavior. The browser validates the exact receipt against its saved review ID and derived host-claim request ID; an old receipt never relabels a newer prepared preview. Historical confirmation is displayed separately from the current lease read. Corrupt or mismatched recovery remains blocked. No current lease authority is inferred from receipts.
